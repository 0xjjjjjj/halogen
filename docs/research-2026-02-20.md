## Executive Summary

The PS2 RE scene is nascent but accelerating. PS2Recomp gives us a foundation, but it's
experimental and incomplete — particularly around VU1 microcode and the Graphics Synthesizer.
The real opportunity: **many early PS2 games retained debug symbols in retail releases**.
If Champions of Norrath is one of them, we get function names for free.

The Snowblind Engine has zero public technical documentation. Everything we learn will be
original. That's a moat.

## Thread 1: PS2Recomp Capabilities

**Status:** Experimental. Developer says "Not ready." But foundational.

### What it does
- Parses PS2 ELF files → extracts functions, symbols, relocations
- Decodes MIPS R5900 including PS2-specific 128-bit MMI instructions
- Translates to C++ literal equivalents
- Supports overlays, function stubbing/skipping, instruction patches
- Configurable via TOML file
- Single-file or multi-file output

### Requirements
- CMake 3.20+, C++20 compiler
- SSE4/AVX for 128-bit ops (128-bit MMI instructions → `__m128i`)
- Runtime layer: `ps2xRuntime` lib for memory, syscalls, hardware simulation

### What's missing
- **VU1 microcode** support is limited — this is the vector processor that handles geometry
- **Graphics Synthesizer (GS)** — not implemented. Needs external runtime
- Not plug-and-play. Needs manual configuration TOML per game

### Build flow
```bash
git clone --recurse-submodules https://github.com/ran-j/PS2Recomp
mkdir build && cd build
cmake ..
make

# Then configure a TOML for your target ELF
```

### TOML config structure
```toml
input = "BASLUS_20565.ELF"
output_dir = "output/"
# Stub external dependencies
stubs = ["printf", "malloc", "free"]
# Skip problematic functions
skips = ["abort"]
```

### Assessment
PS2Recomp gets us a C++ skeleton of the game binary. It won't run, but it's readable,
searchable, and gives us function boundaries. That's the foundation for engine analysis.

## Thread 2: ELF Extraction (Champions of Norrath)

**Game serial:** SLUS-20565 (NTSC-U)
**Disc format:** UDF/ISO9660 (standard PS2 DVD)

### Disc structure
```
SLUS_205.65;1       ← serial/license file
SYSTEM.CNF;1        ← boot config (contains ELF path)
BASLUS-20565/       ← game assets folder
  *.IRX             ← PS2 kernel modules
  *.ELF             ← likely the main executable
  *.STR / *.PSS     ← audio/video streams
  [textures/models]
```

**Main executable:** likely `BASLUS_20565.ELF` or path specified in SYSTEM.CNF

### Extraction tools (without owning disc)
- 7-Zip can open PS2 ISO files directly (UDF filesystem)
- `isoinfo` (Linux) for UDF/ISO9660 navigation
- PCSX2 boots from ISO — can dump ELF from its logs

### Without a binary (current state)
Until we have the ISO, we can:
1. Study SYSTEM.CNF format to know where to look
2. Set up the toolchain to be ready
3. Analyze other Snowblind games if available (BG:DA might be easier to find legally)

## Thread 3: PCSX2 Performance Analysis

The slowdowns are well-documented. This is our performance target:

### Known slowdown triggers
- **Fire/particle effects** — multiple fires on screen → slideshow
- **Cave/underground areas** — lighting? occlusion? still unknown why
- **Many enemies** — expected, but worse than comparable games

### Community workarounds (not fixes)
| Setting | Effect |
|---------|--------|
| Fast Texture Invalidation | Partially helps caves |
| EE Cycle Skipping: 2 | Reduces CPU load, some visual artifacts |
| Multi-threaded GS | Helps on multi-core |
| Internal resolution 4x | Surprisingly doesn't make perf worse |

### PCSX2 source analysis opportunity
PCSX2 has game-specific hacks in source. Champions of Norrath likely has entries.
These hacks are reverse-engineered behavior — reading them tells us what the engine
does that confuses the emulator.

**Target:** `pcsx2/GameDatabase.yaml` and `pcsx2/patches/` in PCSX2 source.

### Key insight
"Fast Texture Invalidation" partially helping in caves suggests the engine is doing
something aggressive with texture cache — possibly streaming textures or using
render-to-texture for lighting/shadows that's incompatible with PCSX2's texture cache.

## Thread 4: Snowblind Engine Architecture

### What we know (very little)
- Called "Snowblind Engine" or "Dark Alliance engine" interchangeably
- Created by Ezra Dreisbach (programmer at Snowblind Studios)
- Designed for overhead third-person hack-and-slash (Diablo-style)
- Used from 2001 (BG:DA) through 2006 (Justice League Heroes)
- **Zero public technical documentation**

### What we can infer from gameplay
- Overhead camera with collision-based level streaming (triggers slowdowns = streaming events?)
- Dynamic lighting (caves have complex lighting, fires are dynamic lights)
- Physics-based particle system (fire = physics particles, not sprite-based?)
- Online multiplayer infrastructure (PS2 network adapter support)
- Likely uses PS2 VU1 for geometry processing

### GDC resources to check
- GDC Vault: search "Snowblind Studios" and "Ezra Dreisbach"
- Any Dark Alliance post-mortems
- PS2 SDK documentation (Sony's PS2 developer docs are now public)

## Risk Mitigations (Pre-Mortem)

### Tiger 1: VU1 Microcode Gap
**Risk:** PS2Recomp can't handle VU1 programs. Geometry processing is invisible to static recompiler.

**Mitigation: Two-layer approach**
- VU1 programs live in `.vudata` ELF section — extract them separately
- Build a VU1 interpreter/emulator layer in C++ that the recompiled EE code calls
- RE:CVX decompilation project pattern: preserve VU1 label structures intact
- VU1 is data-parallel (not control-flow complex) → interpreter is tractable
- Phase 1: stub VU1 calls. Phase 2: implement interpreter. Phase 3: optimize.

```
readelf -S BASLUS_20565.ELF | grep vudata  # check if VU programs are present
```

**Reference:** RE:CVX PS2 decompilation, retroreversing.com/ps2

---

### Tiger 2: Self-Modifying Code / Dynamic VU Loading
**Risk:** DMA transfers load VU programs at runtime. Static recompiler sees them as data.

**Mitigation: N64Recomp overlay pattern**
- Emit `LOOKUP_FUNC(ctx->r25)(rdram, ctx)` for dynamic jumps instead of failing
- Use `RELOC_HI16` / `RELOC_LO16` macros for relocatable code sections
- PS2 VU programs loaded via VIF DMA can be pre-catalogued (finite set per game)
- Build a VIF packet parser to identify all VU programs loaded during gameplay

**Pattern (from N64Recomp):**
```c
// Dynamic jump → runtime lookup
LOOKUP_FUNC(ctx->target)(rdram, ctx);

// Relocatable address → macro
ctx->r24 = S32(RELOC_HI16(section_id, offset) << 16);
```

---

### Elephant 1: GS Replacement (now a paper tiger)
**Original risk:** Replacing the Graphics Synthesizer = writing a GPU driver (6-18 months).

**Mitigation: paraLLEl-GS already exists**
- `github.com/Arntzen-Software/parallel-gs` — Vulkan compute shader GS emulator
- Same author (Hans-Kristian Arntzen / Arntzen-Software) as paraLLEl-RDP, which shipped in N64 Recompiled (production quality)
- GIF tags → Vulkan compute dispatches, VRAM → host GPU memory
- We integrate paraLLEl-GS as the rendering backend, same as N64 Recompiled used paraLLEl-RDP
- This is a **known pattern that shipped** — not greenfield GPU work

**Reference GS docs:** https://psi-rockin.github.io/ps2tek/

---

### Elephant 2: Solo Project Sustainability
**Original risk:** 25K petition ≠ contributors. Solo project burns out.

**Mitigation: Ship tools early, document everything**
- The decomp community pattern: release tools as they work, not when the game runs
- Frame as preservation (resonates with RE community)
- Discord from day 1 — even 20 interested people changes the dynamic
- Modular design makes contribution easy (add one function annotation, help test one subsystem)
- The OG Xbox / PS2 decomp scene is exploding in 2026 — timing is good
- This is explicitly a "flex and reach" project — sustained by curiosity, not obligation
